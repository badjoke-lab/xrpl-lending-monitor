# R3 adapter and reader integration plan — 2026-08-01

Status: controlling R3 contract. R2 is complete on `main` at merge `fb90cbbd3a44337dc0891552f3618581cfc31e1c`.

R3 is local and provider-neutral. It authorizes no hosted provider selection, remote deployment, production mutation, Queue or Cron change, Mainnet change, recovery, qualification, or soak work.

## Objective

Convert the proven SQLite reference runtime into explicit adapter and reader contracts without weakening any R2 invariant or switching the public production reader prematurely.

R3 must establish:

```text
portable phase runtime
  -> StorageAdapter
  -> SchedulerAdapter
  -> ExecutionAdapter

committed portable state
  -> CommittedReader
  -> product read-model mapper
  -> public API compatibility boundary

committed work
  -> PublicationAdapter
  -> immutable verified assets

published and independently verified work
  -> bounded MaintenanceAdapter
```

SQLite remains the reference implementation. Existing release-snapshot, base-plus-overlay, D1 history, and GitHub history readers remain legacy compatibility implementations until an explicit later cutover gate.

## Observed legacy read surface

The current public read path is not one storage model:

- current object reads resolve a configured release snapshot and D1 overlay;
- legacy D1 current-state readers remain available when a release source is not selected;
- history endpoints read legacy D1 tables directly;
- exact history and transaction routes may override D1 reads with Git-backed history assets and exact indexes;
- immutable history publication is generated by separate local build scripts;
- the halted Worker entry still contains legacy collection, Queue, maintenance, and operator paths.

R3 does not rewrite all of these paths in one change. It defines one source-bound compatibility bridge and proves equivalence before any public cutover.

## Adapter contracts

### StorageAdapter

The storage adapter owns only durable collector state. It must expose typed operations for:

- work creation, exact work reads, and sealed scan evidence;
- payload chunk staging and exact ordered reads;
- complete candidate identity staging and committed-only reads;
- commit evidence;
- committed watermark reads;
- transaction-aware finalization;
- canonical runtime export and empty-target restore;
- bounded reconciliation and garbage-collection candidates.

Requirements:

- no adapter method exposes uncommitted candidate rows as public data;
- transaction ownership is explicit;
- idempotent writes compare every identity field;
- no adapter-specific SQL or SDK appears in phase-runtime code;
- export format is the canonical runtime version 3 envelope until superseded by a separately approved migration;
- storage errors are classified without provider-specific strings escaping into core logic.

### SchedulerAdapter

The scheduler adapter owns:

- deterministic message enqueue and exact payload identity;
- claim, lease, stale reclaim, and attempt count;
- retry at a retained message ID;
- terminal failure with no successor;
- atomic completion and one timed successor outbox entry;
- duplicate completion and dispatch convergence;
- scheduler state export and restore.

Requirements:

- one logical phase message has one immutable payload and availability identity;
- retry and lease recovery never create a new semantic message;
- caught-up scan successors use a new `scanSequence` identity;
- phase mutation, current-message completion, and successor reservation share one transaction boundary supplied by the composed runtime adapter.

### ExecutionAdapter

The execution adapter supplies provider-independent inputs and resource accounting:

- network, epoch, base identity, and immutable-base boundary;
- validated head and contiguous ledger estimates;
- normalized source candidates for an exact planned range;
- monotonic operation, request, byte, record, and elapsed counters;
- deterministic successor and retry timing policy;
- classified retryable and terminal failures.

Requirements:

- it cannot advance a cursor or publish rows;
- it cannot silently change the requested ledger range;
- XRPL transport implementations are later deployment-profile components;
- the fixture implementation remains the R3 reference execution adapter.

### PublicationAdapter

The publication adapter is separate from the normal collection scheduler. It owns:

- selecting committed work strictly after a publication watermark;
- verifying work, payload, candidate, ledger, hash, semantic-count, and provenance identity;
- constructing deterministic immutable segments and indexes;
- writing a candidate publication without advancing the publication watermark;
- independently reopening and verifying published assets;
- advancing the publication watermark only after verification;
- emitting compaction authorization for work proven durable in immutable storage.

Requirements:

- staged, committing, finalizing, and failed work are never publishable;
- publication failure cannot halt or advance the collection watermark;
- collection success cannot imply publication success;
- GitHub Actions may execute bounded publication jobs but is not the normal collection clock;
- no hot-store deletion is authorized by upload success alone.

### MaintenanceAdapter

Maintenance is a separate bounded operation. It may delete or compact only records covered by:

1. a committed collection watermark;
2. an independently verified publication watermark;
3. an explicit retention rule;
4. a bounded mutation plan that can be replayed safely.

Maintenance never advances collection or publication watermarks.

## Committed reader contract

### Read fence

Every portable read is bound to one immutable read fence:

```ts
interface PortableReadFenceV1 {
  schemaVersion: 1
  network: string
  epochId: string
  baseIdentity: string
  ledgerIndex: number
  ledgerHash: string
  workId: string
}
```

The fence is derived from the committed watermark. A response cannot combine rows from different fences.

### Generic committed reader

The reference reader provides:

- exact row lookup by semantic class and canonical key;
- deterministic ordered listing by semantic class;
- deterministic ordered listing by source ledger range;
- relationship lookup against canonical relationship IDs;
- work and watermark provenance for every page;
- source-bound opaque cursors containing the read fence and query identity.

Requirements:

- only `collector_committed_reference_rows` or an adapter-equivalent committed view is readable;
- cursors fail when the read fence, query, order, or adapter identity changes;
- unknown or malformed semantic values fail closed;
- no generic reader silently interprets legacy table rows as portable rows.

### Product read-model mapper

Portable rows are mapped into existing product API records only through explicit versioned mappers:

- `current-projection` -> Vault, LoanBroker, and Loan current projections or tombstones;
- `protocol-event` -> activity and transaction event records;
- `object-change` -> object-history records;
- `loan-lifecycle` -> lifecycle records;
- `archived-object` -> deleted-object records;
- `balance-history` -> debt, cover, and loss records;
- `validated-ledger` -> ledger continuity and read-fence evidence.

A mapper must validate the complete canonical value shape and required identity fields. It cannot invent a missing transaction, object, relationship, ledger, hash, or epoch identity.

## Legacy compatibility and cutover states

R3 defines four explicit reader modes:

1. `legacy_only`
   - existing release/base-overlay and D1/Git history paths remain authoritative;
   - portable reads are test-only.
2. `shadow_compare`
   - public responses remain legacy;
   - bounded portable queries run separately and produce comparison evidence;
   - no user response mixes sources.
3. `portable_primary_legacy_fallback`
   - permitted only by a later explicit cutover decision after conformance and shadow evidence;
   - fallback is allowed only for a declared source-unavailable condition before response construction;
   - integrity, identity, digest, cursor, or partial-read failures fail closed and never fall back silently.
4. `portable_only`
   - legacy fallback is disabled;
   - removal requires retained compatibility and rollback evidence.

R3 implementation remains in `legacy_only` and `shadow_compare`. It does not activate portable public reads.

## Source isolation rules

- one response page uses one reader source and one read fence;
- one cursor is valid for one source, query, sort order, and fence;
- a relationship expansion cannot fetch one object from portable state and another from legacy state;
- current and history responses may expose different source modes, but each response declares its source and fence;
- an integrity failure is not an availability failure;
- a source switch requires a new request and cursor.

## Conformance suite

Every adapter implementation must pass the same reusable fixture suite.

### Storage conformance

- exact typed reads and complete identity persistence;
- no pre-finalize visibility;
- atomic finalization and rollback;
- duplicate write convergence and changed-identity conflict;
- export and empty-target restore parity;
- staged, committing, and committed resumption.

### Scheduler conformance

- immutable message identity and availability;
- fresh lease rejection and stale reclaim;
- exact retry identity;
- atomic completion and successor reservation;
- duplicate completion and dispatch convergence;
- terminal halt with no successor;
- export and restore parity.

### Execution conformance

- exact contiguous range delivery;
- resource counters and single-ledger halt;
- reset, epoch, base, parent-hash, and transport classification;
- no cursor or visibility mutation.

### Reader conformance

- committed-only rows;
- stable ordering and pagination;
- fence-bound cursor rejection;
- exact lookup, ledger-range, and relationship queries;
- seven product mappers;
- tombstone behavior;
- malformed value and identity rejection;
- source isolation.

### Publication and maintenance conformance

- committed-only selection;
- deterministic candidate asset generation;
- independent reopen and digest verification;
- publication watermark after verification only;
- collection watermark independence;
- no maintenance before verified publication;
- bounded replay-safe maintenance plan.

## Implementation sequence

### R3A — Adapter interfaces and SQLite conformance

- introduce provider-neutral adapter interfaces without changing runtime behavior;
- wrap the current SQLite reference store and scheduler;
- move composed transaction ownership behind one reference runtime adapter;
- run the existing R2 suite through interfaces;
- prove no Cloudflare, D1, Queue, GitHub, or hosted-provider import in core interfaces.

### R3B — Committed generic reader

- implement read fences, exact lookup, semantic listing, ledger-range listing, relationship lookup, and fence-bound cursors;
- add SQLite reference reader conformance;
- expose no public route.

### R3C — Product mappers and shadow compatibility

- add seven strict product mappers;
- add source descriptors and `legacy_only` / `shadow_compare` selection;
- compare bounded current and history fixtures against legacy serializers;
- produce evidence only; do not change public authority.

### R3D — Publication and maintenance separation

- introduce publication and maintenance interfaces;
- adapt existing local history publication builders behind deterministic candidate/verify steps;
- prove collection watermark independence and verified-publication requirement;
- no remote write is executed.

### R3E — Cross-adapter export, restore, and parent exit

- prove canonical runtime version 3 transfer through adapter interfaces;
- prove reader fence and cursor behavior after restore;
- prove publication and maintenance state transfer;
- pass the complete R3 parent conformance and ordinary CI suite.

## R3 exit

R3 passes only when:

- all four adapter contracts and the maintenance boundary have reference implementations;
- R2 behavior passes unchanged through interfaces;
- the committed reader and seven product mappers pass conformance;
- legacy and portable sources remain isolated;
- shadow comparison produces deterministic evidence;
- publication and maintenance are separate from collection;
- canonical cross-adapter export and restore pass;
- no hosted provider is selected;
- no production path, Queue, Cron, Mainnet flag, recovery, qualification, or soak is changed;
- lint, type-check, complete unit suite, all migrations, build, and browser smoke pass.

R4 begins only after R3 merges with retained evidence. R4 selects and qualifies deployment profiles; R3 does not.
