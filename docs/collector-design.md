# Collector design

## Goal

Maintain Current and History from validated XRPL ledgers without a canonical database.

## Inputs

A run receives or resolves:

- Devnet endpoint(s);
- active channel;
- active epoch;
- last committed ledger index/hash;
- bounded work limits.

## Algorithm

```text
load channel
    |
read latest validated ledger
    |
start = lastCommitted + 1
    |
bounded contiguous ledger scan
    |
verify parent hash chain
    |
filter Lending transactions
    |
derive records once
    |
    +--> Current mutations
    +--> protocol activity
    +--> object changes
    +--> lifecycle
    +--> archived objects
    +--> balance history
    |
build deterministic artifacts
    |
upload
    |
read back / verify
    |
publish channel LAST
```

If `start > latestValidated`, the run is a successful no-op.

## Reuse

The migration should reuse, after provider decoupling:

- `scan-validated-ledgers.ts`;
- `validated-ledger-parser.ts`;
- `affected-nodes.ts`;
- `current-state-overlay.ts`;
- `loan-lifecycle.ts`;
- `deleted-object-archive.ts`;
- `cover-debt-loss.ts`;
- `build-segment-records.ts`;
- current object normalizers and relationship validation.

Do not rewrite these semantics solely because persistence changes.

## Cursor and continuity

The committed cursor is the public channel's ledger/hash.

For the first new ledger:

`ledger.parentHash == channel.lastCommittedHash`

For every later ledger:

`current.parentHash == previous.ledgerHash`

Any mismatch aborts publication.

## Bounded work

A run has explicit limits for:

- ledgers;
- XRPL requests;
- inspected transactions;
- Lending transactions;
- decoded bytes;
- generated bytes;
- wall-clock time.

The exact production numbers are set only after DB-less measurement. Existing legacy limits are evidence, not automatically inherited.

## Idempotence

Re-running the same start/end range produces the same semantic records and digests.

If an asset with the intended immutable generation identity already exists and matches, the run may reuse it.

If it differs, fail closed.

## Scheduling

Target cadence: five minutes using GitHub Actions.

The workflow must use concurrency control so two publishers cannot advance the same channel concurrently.

Scheduled delay is tolerated because every run catches up from the committed cursor.

## Current compaction

Five-minute delta accumulation must stay bounded for public reads.

A compaction job:

1. loads the active base/overlay generation;
2. applies ordered committed deltas;
3. rewrites only affected logical shards/indexes where practical;
4. verifies counts and relationships;
5. publishes a new immutable compacted generation;
6. switches the channel last.

Compaction does not discard history.

## New complete base

A fresh base is a separate heavy workflow.

It pins a fixed validated ledger, runs three type-filtered `ledger_data` traversals to marker exhaustion, creates sharded read models and indexes, validates relationships, and publishes an immutable generation.

A fresh base is not required every five minutes.

## History gap/backfill

Backfill is independent from live operation.

Backfill may only extend a coverage range after:

- every ledger is available;
- hash continuity is verified;
- generated history records pass deterministic validation;
- the new range touches the claimed adjacent boundary exactly.

If historical XRPL data is unavailable, the gap remains public and explicit.

## Failure behavior

Before channel update: safe failure, prior generation remains active.

After verified channel update: run is committed.

A crash after artifact upload but before channel update may leave unreachable orphan artifacts; later cleanup may remove them. Orphan artifacts do not change public truth.
